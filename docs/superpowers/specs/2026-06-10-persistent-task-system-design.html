持久化任务系统完整迁移设计

本阶段只解决任务状态可维护、可恢复和可控制的问题。继续使用本地 JSON 文件，不引入数据库，不同时改设置页、项目 schema 或大规模前端结构。

目标

  • 所有后台工作流统一写入 data/jobs/*.json。
  • 任务状态统一为 queued、running、completed、failed、cancelled。
  • 每次重新执行增加 attempt，保留稳定 job id，便于前端和日志查询。
  • 服务重启后，遗留的 queued 或 running 状态显示为“上次运行中断，可重新执行”。
  • 运行中任务可取消；取消必须终止当前子进程并持久化状态。
  • 重试继续调用现有工作流入口，复用已经生成且未过期的产物。

范围

包含暂不包含
Job Store 状态机、attempt、列表查询、取消状态；最终字幕、英文配音、单段重配、最终成片持久化；统一任务查询和取消 API；前端运行中取消入口。 跨机器任务、数据库、任务历史明细表、断点恢复模型内存、GPU 调度队列、设置页面和 catalog schema migration。

组件边界

  • server/job-store.js：只负责状态校验、原子读写、attempt 和任务列表。
  • server/task-registry.js：只保存当前进程内可取消任务，提供注册、读取、完成和取消操作。
  • server/workflow-job-state.js：把内存任务和磁盘任务合成为 API 可展示状态。
  • server/index.js：本阶段仍负责工作流编排，但所有后台流程必须通过统一 Job Store 和 Task Registry 更新状态。

状态与恢复规则

状态含义允许操作
queued已创建但尚未开始执行。取消
running子进程正在执行。取消
completed流程完成且状态已持久化。重新执行
failed启动、脚本或输出处理失败。重试
cancelled用户主动取消或取消发生在排队阶段。重试

服务启动后不会自动重启模型任务。若磁盘记录仍为 queued 或 running，状态查询将其解释为中断失败，并给出重新执行提示。已有产物仍由各工作流的过期检测决定是否复用。

API

  • GET /api/videos/:id/jobs：返回项目任务列表。
  • GET /api/videos/:id/jobs/:workflow：返回单个稳定 job。
  • POST /api/videos/:id/jobs/:workflow/cancel：取消当前运行或排队任务。
  • 重试继续使用各工作流现有 /run 接口，避免维护第二套执行分发。

错误处理

  • 取消不是失败，错误字段为空，使用 cancellationReason 记录原因。
  • 子进程关闭事件必须先判断任务是否已取消，防止取消后又被覆盖成失败。
  • 无法取消不存在或已结束的任务时返回可读错误，不静默成功。
  • 任务状态写入失败必须记录到工作流日志，但不能造成服务崩溃。

验证标准

  • Node 单测覆盖五种状态、attempt、列表、重启中断解释和 Registry 取消。
  • 所有工作流状态接口在服务重启后仍能读取最近任务结果。
  • 运行中任务取消后，磁盘状态为 cancelled，关闭事件不会改写为 failed。
  • npm run test:node 与 npm run build 通过。
